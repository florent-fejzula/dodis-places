Dodi’s Places → Public Product Plan
Current Product

The app currently exists as a personal tool for discovering my own favorite places in Skopje.

It is built around a simple idea: instead of searching restaurants by ratings, reviews, or generic categories, I browse visually through actual food/drink/place photos and filter using tags.

Examples of current tags include:

Neighborhoods: cair, carshi, centar, karposh, aerodrom, gjorche-saraj
Ambience/mood: luxury, chill, Sunday, restaurant, food, coffee
Food & drink: bread, breakfast, simitPogaca, burek, sandwich, corba, salad, cigKofte, lahmacun, pizza, pasta, sushi, fish, burger, kebab, meats, doner, croissant, pancake, dessert, baklava, iceCream, specialty, juices, cocktails, fullCake, etc.

Each place is represented by a strong visual card with a large photograph, place name and tags.

At the moment the app is private/personal:

No user authentication.
Only my own favorite places exist in the database.
I manually add and maintain them.
The navigation still contains private/admin functionality such as:
Recipes
Tag Manager
Add Place
The current name is Dodi’s Places, where Dodi is my nickname.
Current temporary Firebase URL is something like dodi-s-places.web.app.

The goal now is to turn it into an MVP that is genuinely useful and attractive to the general public in Skopje.

Product Positioning
Core value proposition

This should not become another restaurant directory, Google Maps clone, TripAdvisor clone or ratings app.

The distinctive value is:

Visual cravings on demand.

The user should be able to think:

“I want dessert.”

or:

“I want coffee and a really good-looking croissant in Karposh.”

…and immediately see actual appealing examples of what different places offer.

The app should help people choose based on what visually attracts them, rather than forcing them to read dozens of reviews or open restaurant profiles one by one.

Possible positioning:

Cravings made visual. Pick by what looks good, not just what’s near you.

Another possible description:

A visual guide to Skopje’s best food, coffee and places.

The product should feel like a visual craving engine.

Its advantages should be:

Faster than Google Maps.
Prettier and more curated than TripAdvisor.
Much more structured and useful than browsing Instagram.
More suitable for dine-in discovery than Wolt/Glovo.
Problems the App Should Solve
1. Decision fatigue

People often spend 15–30 minutes deciding:

Where should we eat?
Where should we go for dessert?
Which café looks nice?
Where should I take someone?
What do I actually feel like eating?

The app should reduce this decision to a few minutes.

2. Fragmented discovery

Currently people jump between:

Google Maps
Instagram
TikTok
Wolt
Glovo
TripAdvisor
Friends’ recommendations

The app should provide one clean, curated visual discovery experience.

3. Poor visual discovery elsewhere

Google Maps and review platforms contain inconsistent photos, menus, customer images and irrelevant content.

Dodi’s Places should instead emphasize curated, attractive photography that immediately communicates:

“This is what you could eat/drink here.”

The photos themselves should trigger appetite and help make the decision.

The brand should feel:

Warm
Modern
Urban
Food-focused
Visual
Local
Attractive rather than corporate

It should not feel like a huge generic global restaurant platform.

At least initially, the product should be strongly focused on Skopje.

The working public brand direction is:

Potential domain:

kajdajademe.mk

Possible positioning:

KajDaJademe — Visual guide to Skopje’s best food & cafés.

The local name has advantages because people naturally ask some variation of “kaj da jademe?” / “where should we eat?” in everyday conversation.

Before finalizing the brand, availability should be checked for:

kajdajademe.mk
Instagram: @kajdajademe
TikTok: @kajdajademe

The current Dodi’s Places name and Firebase URL should disappear from the public version.

Firebase can remain behind the scenes while a proper custom domain is connected.

MVP Philosophy

The public MVP should remain simple.

The goal is not to immediately build:

Reviews
Ratings
Comments
Restaurant accounts
Complicated recommendation algorithms
Huge social networking features
Massive restaurant databases
Full monetization infrastructure

The first public version should mainly prove that people enjoy using the core experience:

Open app → visually browse → filter cravings/mood/location → discover appealing place → save/share/go there.

Phase 1 — Separate Public App from Admin Tools
Public navigation

Remove/hide all private functionality from normal users.

Public interface should contain only things such as:

Explore / Home
Favorites
Lists, if implemented
Possibly About later

Private/admin functionality should remain available only to me:

Add Place
Edit Place
Delete Place
Tag Manager
Recipes
Other internal tools

Do not simply expose admin tools and hide buttons cosmetically.

Prefer a real /admin area protected through Firebase Authentication and authorization.

For example:

Normal visitors: public app
My account: admin privileges
Admin routes protected using Angular guards
Firestore rules should also prevent unauthorized writes

Do not rely only on an adminMode frontend boolean for security.

Phase 4 — Authentication

Browsing should not require an account.

Anyone should be able to open the site and immediately explore.

Authentication is useful mainly for personalization.

Use Firebase Authentication.

For MVP, prioritize very simple login methods, especially:

Google Sign-In
Possibly email/password or magic link later

Logging in should unlock:

Favorites

Users can heart/save places.

Possible Firestore structure:

users/{uid}/favorites/...

or another normalized model depending on architecture.

Lists

Potentially allow users to create lists such as:

Date Night
Desserts
Places to Try
Coffee
My Favorites

However, generic Favorites alone may be enough for version 1.

Lists can follow shortly after if they add too much implementation complexity.

Phase 5 — Social and Sharing

Sharing is very important because restaurant decisions are often group decisions.

Users should be able to share:

Individual places
Potentially collections/lists later
Potentially filtered searches later

Example:

“Here are the dessert places I found.”

Instead of sending multiple Google Maps pins, people could send one KajDaJademe link.

Every public place needs a stable shareable URL.

Add proper Open Graph metadata so links shared in apps such as WhatsApp, Messenger and similar platforms display:

Image
Place name
Short description
KajDaJademe branding
Phase 6 — Search and Discovery Sections
Search

Add basic search for:

Place name
Potentially food keywords/tags

Recently Added

Show recently added places based on creation/publish timestamp.

This gives users a reason to return.

Possible homepage section:

New in KajDaJademe

New This Week

Potentially highlight:

New places
New menu photos
Newly added recommendations

This creates ongoing freshness.

Trending

Later, calculate trending based on signals such as:

Favorites
Place opens/views
Map clicks
Shares

For MVP, avoid fake popularity.

Only display Trending once enough activity exists.

Phase 8 — “Surprise Me”

A simple optional stickiness feature:

Surprise Me

The user picks some constraints, for example:

Karposh
Dessert
Chill

Then the app randomly chooses one matching place.

This solves the classic problem of endless indecision.

It should be lightweight and fun rather than a major feature.

Phase 9 — Photo-First Browsing

The visual content is the strongest part of the concept.

The app should continue emphasizing large photography rather than turning into a text-heavy restaurant directory.

Possible later browsing mode:

Gallery/grid
Swipe-based exploration
Large food photography
Tap → place details

Conceptually it can feel a little like Instagram, but structured around useful discovery rather than feeds and influencers.

The photography quality matters enormously.

Avoid filling the database with poor-quality or irrelevant photos merely to increase volume.

Content Strategy

Initially, continue manually curating the places.

That is actually part of the value proposition.

Do not immediately allow restaurants or random users to upload everything themselves.

The product can initially communicate:

These are selected places worth considering.

That keeps image quality, tags and recommendations consistent.

Later, restaurants can potentially submit information for review, but I should remain editorially in control.

PWA / Installation

The app should work perfectly as a normal website first.

Also make it installable as a Progressive Web App.

Users should be able to:

Visit kajdajademe.mk
Use it immediately
Optionally “Add to Home Screen”

Do not make an App Store / Play Store native application a requirement for the MVP unless there is a strong reason later.

A good PWA removes download friction.

Monetization

Do not prioritize monetization before the product has meaningful usage.

Initially keep recommendations trustworthy and curated.

Primary eventual monetization model should be restaurants/cafés paying for additional exposure rather than generic display advertising.

Possible paid products later:

Featured placement

Restaurant appears in a clearly marked Featured section.

Sponsored listing

Higher visibility inside relevant searches/categories.

Must be visibly labeled as sponsored.

Highlighted content

Possibly additional promotional photos, campaign placement or featured collection inclusion.

Today’s Special

Restaurants could potentially promote a temporary offer/menu item later.

However, paid exposure should never destroy the credibility of the recommendations.

Users need to trust that the normal discovery results are genuinely useful.

Advertising Revenue

Generic banner/programmatic advertising is probably not the most attractive business model for Macedonia because CPMs are relatively low and ads could damage the clean experience.

Restaurant partnerships are likely a stronger monetization path.

Monetization Threshold

Do not approach restaurants aggressively before demonstrating real usage.

A rough milestone could be around:

1,000+ meaningful active users

At that point, analytics can support a pitch such as:

X people viewed dessert places this month.
X users opened your restaurant.
X clicked directions.
X saved your place.
X users searched your neighborhood/category.

That is much stronger than simply selling “advertising space.”

Recommended MVP Core Loop

The ideal public experience should be:

User opens kajdajademe.mk.
No login wall.
User immediately sees appealing food/place photography.
User filters by craving, neighborhood or mood.
Results update immediately.
User sees something visually attractive.
User opens the place.
User sees several curated photos and key information.
User either:
Opens Google Maps,
Shares the place,
Saves it.
Later the user returns because KajDaJademe has become their quickest way of deciding where to go.

That loop is the product.

Product Rule to Preserve

Whenever deciding whether to add a feature, ask:

Does this make deciding where to eat faster, more visual, or more enjoyable?

If not, it probably does not belong in the early product.

The key is not to build the most feature-rich restaurant app.

The goal is to build the fastest and most attractive answer to:

“Kaj da jademe?”
